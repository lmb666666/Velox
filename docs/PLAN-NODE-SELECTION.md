## 1. 问题反馈与结论摘要

### 1.1 用户反馈

1. **正确性**：某些功能选择了自定义节点进行测试，但结果中却不仅是选中的节点。
2. **体验**：节点选择器的按钮太小，前端设计不好。
3. **其它**：可能还有更多 bug，需要主动寻找、判断、测试。

### 1.2 结论摘要

- Bug 1 **已复现且比反馈更严重**：选 2 个节点，实际返回 297 个节点（含境外）。
- 根因不是单点，而是**三层问题叠加**：
  - **代码层**：`downgradeNotice` 产出的线路数字编码，其唯一下游 `specToLineValues` 不认识——
    自己产出的格式自己解析不了，最终 `line=''` 导致 itdog 测全部节点；
  - **数据层**：静态节点快照 `assets/nodes.json` 的节点对象缺 `category` 字段（类型却声明必填），
    全新环境下精确选择直接匹配不到分类，退化为「全部节点」；
  - **设计层**：itdog 单目标端点的 `line` 表单字段**只支持线路过滤**，根本不存在「精确节点」能力——
    即使前两层修好，用户选 2 个节点也只能得到「电信+联通全部节点」，而降级提示仅出现在
    运行卡的瞬态状态行里，用户几乎不可能看到。
- 修复核心思路：**把「精确选择」做真**——ping/tcping 的精确节点选择改走 itdog 批量端点
  （`batch_ping`/`batch_tcping` 原生支持精确 node_id，每任务 5 节点），彻底绕开线路过滤限制；
  http/dns 无批量端点、无法精确，在**提交前**明确告知而不是运行中悄悄降级。

## 3. 根因分析（三层根因链）

### 3.1 链路 A：线路编码解析断层（本机实测命中的主路径）

```
用户选 2 节点 → spec = "<id1>,<id2>"
  ↓ service.ts runWithProvider（非批量模式）
itdogProvider.downgradeNotice('ping', spec)
  ├─ spec 非纯线路选择器 → selectNodes(spec) 按 ID 匹配成功（本机缓存含 category）
  ├─ chosen 的分类 = [中国电信, 中国联通] → lines = ['1','2']
  └─ modeOpts.nodes = '1,2'          ← 产出【数字编码】
  ↓ buildTaskSpec('ping')
specToLineValues('1,2')
  ├─ 只认 telecom/电信/unicom/联通/... 【名称】，不认 '1'/'2' 【数字】
  ├─ codes = [] → line = ''           ← 解析断层：空 = 全部线路
  ↓
POST itdog /ping/223.5.5.5  form.line=''  → itdog 测全部节点 → 297 个结果
```

**关键缺陷**：`downgradeNotice`（`src/providers/itdog.ts`）与其唯一下游
`specToLineValues`（`src/nodes.ts`）格式不互逆。链路中途的 status 提示
「已降级为线路过滤: 1,2」只会写进运行卡状态行（`statusLines` 保留最近 6 条、
界面只显示最后一行），**用户实际不可见**。

### 3.2 链路 B：静态快照缺 category（全新环境路径）

- `assets/nodes.json` 结构为 `Record<分类名, 节点[]>`，但节点对象只有 `{id, name}`，
  `NodeInfo.category` 类型声明为必填——**类型与数据不符**。
- `nodes.ts allNodes()` 直接 `Object.values(reg).flat()`，展平后 `category === undefined`。
- 全新环境（无 `~/.cache/itdog-cli/nodes.json`）下：
  `selectNodes` 按 ID 匹配到节点 → `downgradeNotice` 里 `n.category` 为 undefined →
  `CATEGORY_TO_LINE[undefined]` → 全部被过滤 → `lines = []` → 提示「已使用全部节点」→ 同样全节点。
- 附带影响：批量模式帧回填 `categoryToLine(info.category)` 也拿不到线路，运营商显示「未知」。

### 3.3 链路 C：itdog 单目标端点的能力天花板（设计层）

- itdog 单目标端点（`/ping/`、`/tcping/`、`/http/`、`/dns/`）的表单只有 `line` 字段
  （1 电信 / 2 联通 / 3 移动 / 5 境外，空 = 全部），**没有按节点 ID 精确指定的参数**。
- 因此「精确选择」在单目标端点上无论怎么修都只能降级为线路过滤——降级 ≠ 用户意图。
- **突破口**：itdog 批量端点 `batch_ping/`、`batch_tcping` 原生支持 `node_id` 精确指定
  （每任务 1~5 个），且 `service.ts` 已有完整的 5 节点分片串行逻辑——单目标场景复用即可做真。

## 4. 修复设计

### 4.1 修复 1：静态快照 category 注入（修链路 B，低风险，先行）

**改法（代码健壮性优先，同时修数据）**：

1. `src/nodes.ts allNodes()` 展平时注入分组键：
   ```ts
   export function allNodes(): NodeInfo[] {
     const reg = registryLoad();
     return Object.entries(reg).flatMap(([cat, list]) =>
       list.map((n) => (n.category ? n : { ...n, category: cat })),
     );
   }
   ```
   对任意快照格式（有/无 per-node category）都健壮，不依赖数据修复上线顺序。
2. 一次性重生成 `assets/nodes.json`：本地脚本展开现有快照、给每个节点补 `category` 后写回
   （无网络依赖；格式变为节点内也带 category，与 `updateFromHtml` 运行时写出的格式一致）。
3. 单测锁定：`allNodes()` 展平结果每个节点 `category` 必为非空字符串；
   快照文件本身也校验（防再次回退）。

### 4.2 修复 2：`specToLineValues` 接受数字编码（修链路 A 的解析断层）

`src/nodes.ts specToLineValues`：在名称匹配外，直接接受 `1/2/3/5` 数字段：

```ts
else if (['1', '2', '3', '5'].includes(part)) codes.push(Number(part));
```

保证「downgradeNotice 产出 → buildTaskSpec 消费」闭环；即使将来仍走降级路径，
也只会降级到**正确线路**而不是全部节点。

### 4.3 修复 3（核心）：精确选择走批量端点，把「精确」做真

**适用判定**：`mode ∈ {ping, tcping}` 且选择器**非纯线路 spec**（含节点 ID / 关键词，
可被 `selectNodes` 解析为显式节点列表）。

**流程**：

```
单目标 + 精确选择（如 2 节点）
  → selectNodes 解析为节点列表（本例 2 个）
  → 复用批量分片逻辑：chunk 5 个/任务 → ⌈N/5⌉ 个任务串行（片间 chunkSleepMs=600ms）
  → mode 映射：ping→batch_ping 端点（1 目标 × N 节点）；tcping→batch_tcping（带 port）
  → 帧回填复用现有 batchNodeMap 机制（批量帧自带 node_id，回填 name/line/province）
  → buildSummary 使用【原始 mode】（ping/tcping），保证前端表格列与徽标不变
```

**实现要点**（`src/service.ts runWithProvider`）：

- 将现有 `isBatch` 分支的进入条件扩展为：
  `isBatch || (单目标 ping/tcping 且 selectNodes(spec) 命中且 spec 非纯线路)`；
- 命中精确路径时把 `modeOpts.mode` 切为对应批量模式传给 `buildTaskSpec`，
  但 `runTest`/`buildSummary`/`RunResult.summary.mode` 全程保留原始模式；
- status 提示改为用户可读：「已按精确节点执行：2 个节点，1 个子任务」。

**能力边界（不可精确的模式，提交前明示）**：

| 模式 | 精确能力 | 处理 |
|---|---|---|
| ping / tcping | ✅ 批量端点 | 精确执行（本方案） |
| traceroute | ✅ 单节点 | 现状已精确（多选时取第一个，弹窗文案已说明） |
| batch-ping / batch-tcping | ✅ 原生 | 现状已精确 |
| http / dns | ❌ 无批量端点 | 仅线路过滤：**提交前**在表单内联警告，结果页顶部常驻横幅说明 |

**互斥约束（重要）**：批量端点表单**没有** `dns_server_type/dns_server` 参数——
用户同时指定了「自定义 DNS」和「精确节点」时二者不可兼得。处理：
`dnsServer 非空` 时回退线路过滤路径 + 表单内联警告「指定 DNS 仅支持按线路测试，
已忽略精确节点选择」，让用户二选一，不做静默取舍。

### 4.4 修复 4：降级可视化（结果可解释）

- `RunResult.summary` 增加 `requestedNodes?: number` 与 `degradedTo?: string`
  （如「电信+联通线路」）；service 层在发生任何降级时填入。
- 前端结果页元信息行显示徽标：`选中 2 · 实测 190（按线路降级）`，点击可见说明。
- 降级提示文案用运营商名（「电信、联通」）替代裸数字（「1,2」）。

## 5. 节点选择器前端重设计

### 5.1 现状问题

- 「逐节点选择」按钮是小号 `size="sm"` 按钮（约 100×32px），与「刷新」图标按钮挤在一行，
  视觉权重远低于其功能重要性（它是精确测试的唯一入口）；
- 选择结果只以一行小字 `节点选择: <spec>` 呈现，节点 ID 串对用户不可读；
- 弹窗内无分组全选；`picked` 状态与 spec 不同步（点了预设后再开弹窗，旧勾选仍在）。

### 5.2 新交互设计

触发区改为「全宽选择器条 + 预设 chips」两行结构，选择器条承担状态展示与入口双重职责：

```
┌ 节点选择 ────────────────────────────────────┐
│ [全部] [三网] [电信] [联通] [移动] [海外] [京沪广深]        [⟳] │
│ ┌──────────────────────────────────────────┐ │
│ │ 👥 已选 2 个节点：湖北十堰-电信、山东济南-联通   ⌄ │ │  ← 全宽触发条 h-11，
│ └──────────────────────────────────────────┘ │     点击打开弹窗
│ ℹ http/dns 模式仅支持按线路测试，精确选择将降级      │  ← 仅在需要时出现的内联提示
└──────────────────────────────────────────────┘
```

触发条文案规则：

| 状态 | 文案 |
|---|---|
| 未选（all） | `全部 293 个节点` |
| 纯线路 | `电信 + 联通 线路节点` |
| 精确选择 | `已选 2 个节点：湖北十堰-电信、山东济南-联通`（超过 3 个折叠为 `等 N 个`） |
| 批量 + N>5 | 追加 `· 将创建 ⌈N/5⌉ 个子任务` |

弹窗内增强：

- 每个运营商分组标题行加「全选/取消全选」；
- 打开时从当前 spec 反解析回 `picked`（消除状态不同步）；
- 页脚已选计数 + 「应用」，应用后触发条立即刷新摘要。

### 5.3 涉及文件

- `web/src/components/NodePicker.tsx`（重写触发区与弹窗逻辑）
- `web/src/components/TestForm.tsx`（节点选择区内联降级警告，替换原 hint）

## 8. 风险与权衡

1. **上游请求次数增加**：精确 N 节点 = ⌈N/5⌉ 个任务（对比线路过滤的 1 个任务）。
   片间已有 600ms 间隔；293 全选走精确路径会拆 59 个任务——**纯线路 spec（all/telecom/…）
   不走批量路径**，仍走单目标端点，避免最常见场景的请求放大。
2. **批量帧字段差异**：批量帧不带 name/province，依赖 batchNodeMap 回填（机制已存在并经
   批量模式长期验证）；回填失败时显示「(未知节点)」而非丢弃。
3. **指定 DNS 与精确选择互斥**：批量端点无 DNS 参数，属 itdog API 能力边界；
   方案选择「明示互斥、用户二选一」而非静默丢弃任一方。
4. **itdog 接口变更风险**：批量端点参数与单目标一致来自官方页面表单，风险等同现状；
   若上游调整 `node_id` 上限（当前 1~5），分片常量集中在一处可快速调整。
5. **前端无测试设施**：`frameOk` 口径修复以「后端口径为唯一真源」+ 双侧注释互指，
   待将来引入前端测试设施后补契约测试。
